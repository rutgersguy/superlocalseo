## Reopened follow-up — 2026-10-15

The follow-up review found gaps in the earlier closure. The remaining code fixes are now implemented; deployment/production QA is recorded below when complete.

- **Promo redemption:** coupon `duration=once` is not a customer redemption limit. The old resolver accepted a code despite a finalized invoice already carrying it; a before/after harness reproduced acceptance on the old source and rejection on the new source. Eligibility now reads paginated Stripe invoice history plus the customer discount, enforces first-transaction restrictions when configured, and rejects ID-based bypasses. Checks run during preview and again under the existing client confirmation lock. Committed pending attempts retain their original idempotency key for ambiguous retries. Each promotion code is redeemable once per Stripe customer; different offers remain possible, and existing ongoing discounts remain inherited when the field is blank. Finalized invoices count even when later voided/refunded; unfinalized drafts do not. Review this conservative policy before introducing repeat-use marketing campaigns.
- **Renewals:** Stripe prices the full recurring items with applicable ongoing discounts; once discounts and repeating discounts expiring before renewal are excluded. Renewal estimates use invoice total rather than customer credit balance. Existing discount IDs preserve previously redeemed offers. Both subscribe and change-plan screens show the expected next renewal. Annual catalog prices still mean twelve months for the price of ten, including add-ons.
- **Review destinations:** creating a location resolves and saves a Google business place ID when exactly one candidate matches the address and a business-name/phone/website signal. Address-only place IDs, wrong addresses, and ambiguous candidates are rejected. Identity edits clear a previously inferred destination unless an explicit ID is supplied; lookups cannot overwrite newer edits or a manual ID. This is Places lookup, not Google profile sync. Unresolved businesses retain an honest manual/support fallback. `scripts/backfill-location-places.cjs` defaults to dry-run; `--apply` performs verified matches only and explicitly excludes Stephen by client ID and email.
- **Map reproduction:** production report `15ee2c73-873b-4f44-9463-b0cf1a2bffc9` logged DataForSEO task `40102` after retries. Two failed points were queried sequentially: the original coordinates returned `40102`, zero results; seven-decimal coordinates plus explicit `15z` returned `20000` with 8 and 13 listings, respectively. These four diagnostic calls cost $0.008. Provider documentation identifies `40102` as “No Search Results”, not proof of throttling. The old implicit 17z viewport was too narrow for these points. Maps now use explicit neighborhood zoom, seven-decimal coordinates, depth 50, and up to two DataForSEO task attempts. See [Maps API](https://docs.dataforseo.com/v3/serp/google/maps/live/advanced/) and [error codes](https://docs.dataforseo.com/v3/appendix/errors/).
- **Map reliability limits:** eight provider operations maximum across concurrent scans in one API process; eight-minute scan budget; BrightLocal submission/poll timeouts 15 seconds and DataForSEO timeout 30 seconds. BrightLocal polls reuse the paid request ID; failed results/timeouts also fall back. Logs identify report, provider and grid coordinate. At least 80% verified coverage is required for visibility percentages; insufficient maps show an error and unknown points without misleading summary percentages. Existing low-coverage reports receive this treatment when read. Unknown is never converted to absence. Review concurrency, zoom and 80% threshold with more provider data. Provider calls may consume the documented scan allowance; this does not change quota pricing or add overage charges.
- **Billing counters:** actual keywords per active location and accepted/unexpired invited seats (including the owner) appear in Billing; archived locations do not count.
- **Small regressions:** January offers prior years with completed months; the version-literal guard includes TSX; Rankings derives current-plan behavior without a dated version literal; environment comments identify legacy price IDs. The installed Stripe SDK/API remains 2024-06-20, which supports the singular invoice discount field; an API upgrade requires a separate compatibility check.
- **Webhook atomicity:** client updates, location archives, billing-change reconciliation, queued notifications, and the event receipt share a database transaction. A failure-injection test makes receipt insertion fail and proves both account effects and queued email roll back. External effects drain from `billing_effects` after commit, under row locks, and skip events superseded by a newer account/subscription state. Payment email uses a deterministic Resend idempotency header; ambiguous attempts older than 23 hours are held for operator review because the provider retains keys for 24 hours. EMR deprovisioning is idempotent; legacy upstream suspension retains its existing nonfatal reconciliation policy. This does not claim exactly-once execution across external providers.
